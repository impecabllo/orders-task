# Решение

## Статистика заказов

`GET /customers/:id/daily-totals` возвращает `gross` до скидок, `net` по фактически оплаченным суммам и `discount` как разницу между ними. Поле `total` по-прежнему равно `gross`. В расчёт входят заказы в актуальном статусе `paid`. Период включает обе запрошенные даты, дни без заказов содержат нули.

Синхронизация и вебхуки используют общую нормализацию заказа. `amount` и `amountPaid` сохраняются и суммируются в целых копейках. Конвертация в рубли происходит при формировании ответа. Десятичный перенос сохраняет целые копейки, которые могла потерять операция `Math.floor(rub * 100)`, например для `0.29`. Для входа с долями копейки сохранил прежнее правило отбрасывания.

## Причины расхождения

1. **Смещение часового пояса на дату запроса.** Исходный сервис применял текущее смещение `Europe/Berlin` ко всем заказам `c_7`. 29 марта 2026 года Берлин перешёл с UTC+1 на UTC+2. Например, заказ `o_02357` создан в `2026-03-29T22:40:08Z`, когда в Берлине было уже 00:40 30 марта. Исходный сервис отнёс 9 306 ₽ к 29 марта. В новом расчёте `Intl.DateTimeFormat` определяет местную дату отдельно для каждого `createdAt`.
2. **Параллельная доставка версий заказа.** Исходный сервис сравнивал `updatedAt` перед отдельной безусловной записью. В прогоне исходной версии заказ `o_02281` остался в статусе `paid` с `updatedAt` 03:50:18 UTC, хотя вебхуки доставили более свежую версию `refunded` с временем 04:50:18 UTC. В отчёте за 29 марта появились лишние 3 675 ₽. При конфликте вставки PostgreSQL теперь проверяет `updatedAt` в самом `UPDATE`. Повтор и более старая версия не перезаписывают актуальные данные.

Запустил исходный сервис с приложенным API и отдельной базой, выгрузил его ответ после синхронизации и вебхуков и сравнил его с пересчётом сырых данных по `createdAt`, часовой зоне клиента и последней версии каждого заказа. Сравнение по `gross` отделяет ошибки группировки и статусов от добавления скидок.

| Дата | Исходный `total`, ₽ | Исправленный `gross`, ₽ |
| --- | ---: | ---: |
| 2026-03-27 | 24 736 | 24 736 |
| 2026-03-28 | 58 233 | 58 233 |
| 2026-03-29 | 47 639 | 34 658 |
| 2026-03-30 | 52 201 | 59 684 |
| 2026-03-31 | 44 064 | 35 401 |

## Совместимость и допущения

- В API 1 177 из 5 030 заказов пришли без полей скидки. Без `amountPaid` считаю `net = gross`. Явный ноль означает нулевую оплату. Если оплата указана, беру её из `amountPaid` независимо от `discountPercent`. Последний встречается и как число, и как строка.
- Миграция `002_order_amount_paid.sql` добавляет nullable-колонку. Для ранее сохранённых строк работает то же допущение о неизвестной оплате. Повторный синк заполняет колонку, если пришла сумма для совпадающей версии заказа. Прогон миграции поверх исходной схемы сохранил все 5 030 строк.
- День заказа определяется по `createdAt`, как в исходном сервисе. В API встречаются суммы строками и временные метки без зоны. Для последних сохранено допущение UTC. Сигнатура `createContainer(db, api)` и интерфейс `OrdersApi` сохранены.

## Проверка

- `npm run typecheck` и `npm test` прошли. Vitest выполнил 32 теста на PostgreSQL 16. Добавил проверки перехода на летнее время, расчёта копеек, синхронизации и обновления оплаты вебхуком, пополнения старой записи и параллельной доставки версий. Тест перехода на летнее время воспроизводит ошибку на исходном коде.
- `result.json` сохранён из HTTP-ответа после полного прогона с нуля на PostgreSQL 16 и приложенном образе `orders-mock:3`. Синхронизация обработала 52 страницы и 5 030 заказов без ошибок. Все 92 доставки вебхуков получили HTTP 200.
- Отдельно пересчитал все пять строк из данных `/orders` и тел вебхуков, используя десятичную арифметику и правила `Europe/Berlin`. Все поля совпали с HTTP-ответом. Проверил `total = gross` и `discount = gross - net` для каждой даты.

Для повтора после загрузки образа под свою архитектуру запустите Compose с чистой базой. В проверке сервис слушал порт 3205, поскольку 3000 был занят.

```sh
docker compose up -d --wait
npm ci
npm run migrate
PORT=3205 npm start
```

В другом терминале дождитесь завершения каждой команды.

```sh
curl -fsS -X POST http://localhost:3205/sync
docker compose run --rm orders-api webhooks --target http://host.docker.internal:3205/webhooks/order
curl -fsS 'http://localhost:3205/customers/c_7/daily-totals?from=2026-03-27&to=2026-03-31' -o result.json
```

## Что бы доделал

Добавил бы метрику по оплаченным заказам без `amountPaid`, чтобы отслеживать полноту данных об оплате. Для больших отчётных периодов проверил бы стоимость выборки и группировки и сравнил текущую реализацию с агрегацией в PostgreSQL.
