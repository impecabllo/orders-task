# Решение

## Статистика заказов

`GET /customers/:id/daily-totals` считает заказы с текущим статусом `paid`. `gross` показывает сумму до скидок, `net` показывает фактическую оплату. `discount` равен `gross - net`, а `total` по-прежнему равен `gross`. Границы периода включены. За дни без заказов сервис возвращает нули.

Синк и вебхуки обрабатывают суммы одинаково. Сервис хранит и складывает `amount` и `amountPaid` в целых копейках, а при ответе переводит их в рубли. При `Math.floor(0.29 * 100)` можно потерять копейку. Поэтому сдвигаю десятичную точку в записи суммы. Если во входных данных есть доли копейки, отбрасываю их, как и раньше.

## Причины расхождения

1. **Смещение часового пояса на дату запроса.** Исходный сервис применял текущее смещение `Europe/Berlin` ко всем заказам `c_7`. 29 марта 2026 года Берлин перешёл с UTC+1 на UTC+2. Например, заказ `o_02357` создан в `2026-03-29T22:40:08Z`, когда в Берлине было уже 00:40 30 марта. Исходный сервис отнёс 9 306 ₽ к 29 марта. В новом расчёте `Intl.DateTimeFormat` определяет местную дату отдельно для каждого `createdAt`.
2. **Параллельная доставка версий заказа.** Исходный сервис сравнивал `updatedAt` перед отдельной безусловной записью. В прогоне исходной версии заказ `o_02281` остался в статусе `paid` с `updatedAt` 03:50:18 UTC, хотя вебхуки доставили более свежую версию `refunded` с временем 04:50:18 UTC. В отчёте за 29 марта появились лишние 3 675 ₽. При конфликте вставки PostgreSQL теперь проверяет `updatedAt` в самом `UPDATE`. Так при повторах и доставке не по порядку сохраняется последняя версия.

Запустил исходный сервис с приложенным API и отдельной базой, сохранил ответ после синка и вебхуков и пересчитал суммы по исходным данным. Для каждого заказа брал последнюю версию и переводил `createdAt` в часовой пояс клиента. Ниже сравнил суммы до скидок, чтобы проверить группировку по дням и учёт статусов.

| Дата | Исходный `total`, ₽ | Исправленный `gross`, ₽ |
| --- | ---: | ---: |
| 2026-03-27 | 24 736 | 24 736 |
| 2026-03-28 | 58 233 | 58 233 |
| 2026-03-29 | 47 639 | 34 658 |
| 2026-03-30 | 52 201 | 59 684 |
| 2026-03-31 | 44 064 | 35 401 |

## Совместимость и допущения

- В API 1 177 из 5 030 заказов пришли без полей скидки. Без `amountPaid` считаю `net = gross`. Явный ноль означает нулевую оплату. Если оплата указана, беру её из `amountPaid`. `discountPercent` в API встречается числом и строкой.
- Миграция `002_order_amount_paid.sql` добавляет колонку, в которой у старых записей хранится `NULL`. Повторный синк заполняет её, если API прислал сумму для той же версии заказа. Проверил миграцию на исходной схеме. Все 5 030 строк сохранились.
- День заказа определяется по `createdAt`, как в исходном сервисе. В API встречаются суммы строками и временные метки без зоны. Метки без зоны считаю временем UTC. Сигнатура `createContainer(db, api)` и интерфейс `OrdersApi` сохранены.

## Проверка

- `npm run typecheck` и `npm test` прошли. Все 44 теста прошли с PostgreSQL 16 на Node 20.0 и 22.18. В тестах проверил переход на летнее время, копейки, синк, вебхуки, обработку ошибок API и параллельный запуск миграций. Тест перехода на летнее время воспроизвёл ошибку в исходном коде. `npm audit` не нашёл известных уязвимостей в зафиксированных версиях зависимостей.
- `result.json` сохранён из HTTP-ответа после полного прогона с нуля на PostgreSQL 16 и приложенном образе `orders-mock:3`. Синхронизация обработала 52 страницы и 5 030 заказов без ошибок. Все 92 доставки вебхуков получили HTTP 200. После ревью повторил сценарий на чистой базе и получил тот же ответ.
- Отдельно пересчитал все пять строк по данным `/orders` и вебхуков с десятичной арифметикой и часовым поясом `Europe/Berlin`. Суммы совпали с HTTP-ответом. Проверил `total = gross` и `discount = gross - net` для каждой даты.

Для повтора после загрузки образа под свою архитектуру запустите Compose с чистой базой. В проверке сервис слушал порт 3205, поскольку 3000 был занят.

```sh
docker compose up -d --wait
npm ci
npm run migrate
PORT=3205 npm start
```

В другом терминале дождитесь завершения каждой команды.

```sh
curl -fsS -X POST http://localhost:3205/sync
docker compose run --rm orders-api webhooks --target http://host.docker.internal:3205/webhooks/order
curl -fsS 'http://localhost:3205/customers/c_7/daily-totals?from=2026-03-27&to=2026-03-31' -o result.json
```
